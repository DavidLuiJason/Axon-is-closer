### 00.2 THE FOUNDATION LAWS (FL1 to FL13)
**FL1. The top view (the maze law).** Walking in a random direction is walking into a maze without having looked at it from above. Whoever holds this roadmap must always look at the whole of AXON from the top (Part 5E map) before choosing a direction. A direction chosen without the top view is a defect, even if it works. (Owner's words, to be kept: "Whatever is responsible for AXON and has this roadmap must always look at it from a top view. Otherwise we are destined to fail and come back.")
**FL2. Read everything, then act.** An AI that receives this roadmap and the project zip must read ALL of it, reconsider the whole project (not only the stage in progress), then act. Skimming the start and end, or searching for keywords, is a breach. Ask: can the structure carry not only this system but every system still to come? Is it sound? What will collapse, and how? What can be done now that stops repeating work? What have we been doing that costs time and effort? Write the answers down (Top-View Check, 00.4).
**FL3. The plan reaches the end of the app.** A plan that covers only the piece in hand is not a plan. Every plan, stage and tool leaves room for the complete AXON (Part 5E). "We did not account for that" is not an acceptable reason for a rework. The AI tools' habit of working only with what they currently have is named here as the thing to stop.
**FL4. Success and progress first; no repeating.** Every step achieves the maximum progress and success. What can be done once is not done five times; a problem one prompt can solve does not take ten. This is NOT permission to guess or rush: (a) work with understanding; (b) size a job to what the builder is PROVEN to carry (Rule 1) and give it the largest such job, not the smallest; (c) every script is simulated on real files before the owner receives it (Lesson 9); (d) anything the owner had to repeat becomes built in (Repetition Register, 00.5). **Two-Strike Rule:** if the same problem is unsolved after two attempts, STOP fixing, write a top-view analysis (which layer, which assumption failed) and re-plan before a third attempt.
**FL5. The dictionary is core, NOT cargo.** (Owner decision, 2026-10-12; replaces the v13.x idea of keeping it out of the app and the export as "cargo".) The dictionary is AXON's understanding of English: a primary, basic need that conversational awareness will lean on heavily. It is never removed, never left out of the app, never left out of the export, never treated as optional weight. Size is handled by SEARCHABLE compression (FL6), not by throwing data out. It must be reachable with no restriction from the Dictionary screen and from a search typed in the main chat.
**FL6. The Searchable Compression Law.** Anything heavy (the dictionary today; every other language, tool data and media later) is stored (a) as small as possible WITHOUT losing anything (Rule 7; quality material is never degraded); (b) in independent blocks, each hash-checked, with an index so a lookup opens ONLY the block it needs; (c) in as FEW FILES as the design allows, because every tool in the chain pays per file (FL7, 4.2l); (d) described by a manifest that the guard checks and that grows by itself (Rule 12); (e) reached by the app through one interface (the knowledge slot, F3) so the physical form can change without touching screens or brain. Reason: the project must stay small enough to hand to AI tools and import anywhere, now and at ten times the size. Each use states the disadvantages (Rule 7).
**FL7. Find out why, by measurement; assume neither side.** (Owner decision, 2026-10-12: fixing the Google AI Studio push is COMPULSORY.) AI Studio belongs to a very large company and is likely able to handle large projects. So the failure is either something about OUR project (arrangement, file count, our code or config) or a real AI Studio limit. Stage G4 designs controlled experiments that separate the two and the result decides what we change. "AI Studio cannot carry thousands of files" is a hypothesis until G4 measures it. The same applies to the export: it was an earlier AXON problem too, and the owner has seen exports differ without learning why (OWNER-REPORTED); that is a defect to explain, not live with.
**FL8. The AXON export is the way home, and it must be perfect.** (Owner decision, 2026-10-12.) The owner keeps editing in Google AI Studio. If the push and the export are both untrusted, no edit can reach GitHub. So the AXON source export is fixed FIRST and completely (G2) and must be provably equal to the repository (tools/compare-dirs: 0 missing, 0 extra, 0 different). Until G2 is proven, the old rule holds (the app's Export is not used as a source). After G2, the fixed export (from the AI Studio preview and from the installed app) is the normal way a project leaves AI Studio and enters GitHub through the automatic unpack (Part 5D), where the guard checks it. This answers "if we do not use the push and not the export, what do we use?": the fixed export, while we find why the push fails.
**FL9. Plan first, never repair in the dark.** Every piece of work belongs to a stage (Rule 5). A symptom is written down, tied to its layer and cause, and handled in plan order. Before any stage prompt is sent, the Foundation Check (Part 1) AND the Top-View Check (00.4) are written down.
**FL10. The chat is the one control surface, and AXON tells the truth about itself.** (Owner decision, 2026-10-14.) Every capability AXON has or will have (text tools, dictionary, the source export, settings, background jobs, and later collage, video, text to speech, file work) must be (a) declared in ONE place, the capability registry, with its chat ACTIONS: what it does, what it needs from the owner, what it returns; (b) reachable from the main chat by an ordinary request; (c) able to ASK for what is missing, with choices when choices exist (a collage style, a voice, which kinds of data an export should carry), through the brain's follow-up mechanism; (d) described ONLY from that registry, so "what can you do?" lists exactly what exists and says plainly what is unavailable, needs a permission or a screen, or is not built yet; AXON never claims an ability the registry does not hold and never hides one it holds; (e) honest about results: it says what it did, what it saved and where, and what failed. A tool, screen or generator is not done until its chat actions are declared and tested. A capability may also have a screen, but the screen is never the only way in. Permissions stay advisory until enforced (G5a, G5b); a capability that touches the device asks first and keeps an undo copy (R2). ## PART 1. The owner's building rules (must be applied before EVERY plan and EVERY stage)
The owner's sayings are the main rule of the whole project.
**Rule 1. Do not put an elephant on a toothpick.** Before giving any job to anything (a builder, a machine, the phone), find out how much it can carry, then size the job to fit. Example: a 66 MB dictionary into a build on a machine with 1.2 GB of memory; the build died. We never measured what the machine could carry.
**Rule 2. Do not put a house of 100,000 pounds on a foundation that holds 30,000.** The foundation must be at least as strong as everything planned above it. Example: a language layer, tools and personality planned on a base not yet measured (build machine, app size, phone memory, test gate).
**Rule 3. Build from the foundation up, never from the sky down.** Lowest layer first; do not build the roof and then look for a wall. Example: the dictionary (a roof item) went into the app before the slot that receives knowledge existed and before the build could carry it.
**Rule 4. One builder, one small job, one proof.** An overloaded builder fails and makes the work worse for everyone. A prompt holds ONE job, at most about seven steps, and ONE clear proof. Do not mix installing, testing, building and diagnosing in one prompt; split into prompts in order.
**Rule 5. A plan before work, not repairs in the dark.** Every piece of work belongs to a stage in Part 6. A bug is written down, tied to its layer and fixed in plan order unless it blocks the foundation. If we find ourselves fixing at random, stop and re-plan.
**Rule 6. Measure first, then design, then build, then prove.** Never design on a guess; record the number, then design to fit.
**Rule 7. Compress big data that can be compressed; never compress what needs quality.** (Owner rule, 2026-10-10.) Large data such as the dictionary is handed over, stored and shipped compressed whenever that loses nothing. The dictionary is 66.6 MB as plain files and 16.3 MB compressed (MEASURED, standard compression; a stronger method gives 10.3 MB, MEASURED, but needs extra code to open). Things that need quality (images, audio, video, anything the owner will look at or edit) are not squeezed in a way that loses detail; text is only compressed without loss. The Director states the disadvantages each time: the phone must decompress before use (a little time and code); compressed data cannot be read in the middle unless split into independent pieces; already-compressed data (most images) does not shrink. For the dictionary the advantages are larger: a much smaller download and hand-over, fewer bytes for every machine. **(v14.0, owner, 2026-10-12) Compression stays SEARCHABLE: independent blocks with an index, a lookup opens only the block it needs, in as few files as possible (FL6). ## PART 5C. The Move Protocol (how the project travels without losing anything)
The hub: the GitHub repository of the current version is the single source of truth. AI Studio is a workspace; its copy is never trusted until the guard has passed on it. Four kinds of move: (a) repository to a new repository (a new repository per version); (b) one AI Studio account to another; (c) GitHub into AI Studio and back (editing there); (d) through Grok (shell work).
Every move follows the same steps (the source is ALWAYS the GitHub repository or a Director-built zip, never an app export, 4.2j):
(1) BEFORE leaving: the guard passes on the source (a green cloud build shows `GUARD OK`, or Grok runs `node tools/guard.mjs`). The last good zip and a restore tag exist. (2) CARRY the whole project, including tools/ (guard.mjs and files.lock). The lock holds only relative paths, so it works in any repository or account. (3) AFTER arriving: the guard runs on the destination (cloud build on the destination repository, or Grok on an exported zip). Nothing else happens until it passes. (4) If it FAILS: stop. The failure names every missing or changed file. Restore them from the source, run the guard again, then continue. Never push a project whose guard failed. (5) A deliberate removal or rename is recorded by a builder with a shell: `node tools/guard.mjs --forget PATH` (then `--ratchet`). A new dictionary version is accepted with `--accept PATH`.
Branch rule for editing in AI Studio (from the first AI Studio edit session): AI Studio pushes to a side branch named `studio`, never main. The cloud build runs on every branch (workflow v13.2), so the guard checks pushed work first. Only a green branch is merged into main (GitHub: Pull requests, New pull request, base main, compare studio, Merge); the Director gives the exact clicks at the first merge. The ratchet then locks new files by itself.
AI Studio standing rules (the owner pastes this ONCE into the AI Studio project's system instructions, in every account and every new AI Studio project; its purpose is to stop silent deletions): "STANDING RULES FOR THIS PROJECT. 1. Never delete, rename, move or shorten any existing file or folder unless my message names that exact file. 2. Never touch the folders .github, tools or public/dictionary, or the files .gitignore, .nvmrc and package.json, unless my message names that exact file. 3. ## PART 5H. The brain's structure (v15.1; owner decision 2026-10-15; DESIGN, with the status of each stage)
### 5H.1 The problem, measured
See Finding M (4.2zb): today the brain is a router. A message goes to the first provider that recognises it by its own text matching; three places each hold a piece of "understanding"; nothing is shared; there is no dialogue state, planner, checker or reply composer. Adding recognised phrases to this makes it larger, not smarter (FL13), and the number of phrases needed is unbounded. The owner's law FL12 says the brain is a designed system and everything in the chat goes through it.
### 5H.2 The pipeline (ten stages; each is a typed, pure, traceable step)
| Stage | Job | Built in |
|---|---|---|
| 1 Intake | make the Utterance (text, place, time, id) | B1 |
| 2 Reading | split into language and MATERIAL (code, quotes, pasted text) that is never interpreted; symbols and punctuation (L1 exists in src/brain/symbols) | B1 wraps it |
| 3 Analysis | tokens, real lemmas, parts of speech and word concepts (WordNet synsets) through the knowledge slot (core dictionary and, later, the user dictionary); multi-word entries | B2 |
| 4 Meaning | the Frame: speech act (ask, command, teach, correct, greet, thanks, chat, unknown), predicate concept, typed arguments (slots) pointing at spans, material references, a confidence and the alternatives | B3 |
| 5 Resolution | match the frame to ACTION SCHEMAS declared in the capability registry by meaning: concept distance (synonym 1.0, then hypernym and hyponym distance, decaying), act match, slot completeness; RUN_AT 0.8, ASK_AT 0.5 (existing constants in src/brain/matcher.ts); below ASK_AT AXON says it does not understand | B4 |
| 6 Dialogue | pending questions and choices (src/brain/asking.ts), follow-ups, continuations ("more"), references to earlier messages, "it" and "that", the topic | B5 |
| 7 Planning | one or several instructions in a message (L3), order, risk and irreversibility questions, permissions, ask for what is missing (TH1 steps 3 and 4) | B6 |
| 8 Execution | capability handlers run through the kernel with TYPED arguments; a handler never parses free text | B1 (legacy handlers), then each capability moves as B4 and B5 retire the legacy ones |
| 9 Verification | check the result against the request; evidence labels PROVEN, CHECKED, REPORTED, UNSURE (Part 7 item 11); find problems and recheck (TH1 steps 6 to 8) | B6 |
| 10 Response | compose the reply from the structured result in the voice and tone of Part 7 items 8 and 10; never raw plan text | B6 (B1 removes the stray foundation block, CF1) |
Every stage writes a trace entry (stage, state, note) so "how did you understand me" (R2) is a view of real data, and tests can assert on it.
### 5H.3 How understanding works without phrase lists
Words become lemmas (src/brain/dictionary/morphology.ts exists), lemmas become concepts (the dictionary's synsets and relations; 120,254 sense relations and 234,810 synset relations are in the data), a message becomes a Frame from generic English structure (an imperative starts with a verb, a question inverts or uses a wh-word, a teaching message says what something means), and the Frame is matched to what each capability says it MEANS: "count" and "tally" and "enumerate" are one concept, so a new wording needs no new entry. Example phrases stay in the registry as documentation and as a test corpus. Ambiguity asks with choices. A capability's handler receives arguments, never the text.
### 5H.4 Migration without breaking anything (the strangler method)
B1 wraps today's providers as LEGACY HANDLERS inside the Execution stage and proves nothing else changed: a GOLDEN TRANSCRIPT (tests/fixtures/brainGolden.json, recorded from the code as it is before B1) is compared field by field after every Phase B stage; only the changes a stage names may differ. The LEGACY REGISTER (src/brain/mind/legacy.ts) lists every legacy handler with the stage that retires it (local rules and the dictionary provider: B4; taught meanings: B5; the foundation fallback: B6); a test fails if a provider exists that is not in the register. tests/brainBoundary.test.ts holds the ratchet list of files that import the brain. A static test forbids regular-expression literals inside src/brain/mind (no phrase matching in the new stages).

## PART 7. The language design (carried from v12.6, in simple words)
(1) **English dictionary.** Open English WordNet 2025 (4.2). "Complete" means everything in that source with its definitions, examples, parts of speech, relations and forms, and its name and release recorded and shown on request. It does NOT mean every word of English. Inflected forms come from rules plus an exception list. (2) **One dictionary per language.** English is installed with the app. Other languages come later, first by a builder, later by in-app download with a checksum. The owner dislikes the word "pack". Inside a dictionary the data is split into small pieces (shards) so only what a lookup needs is loaded; the owner never sees them. (v14.1: "pack files" in G3 are an internal storage form, never shown to the owner or named in the app.) (3) **Size and loading.** The dictionary is opened only when needed, never at app start. (4) **Word links.** Words in one meaning are linked as exact, near, depends-on-context, related, or opposite. Only exact and near may replace a word. Phrases point to meanings, and meanings point to actions AXON can run. When a message does not match, words are replaced by linked words and the match is tried again; each replacement lowers the score; a weak guess never runs anything (run at 0.8 or higher; ask "Did you mean" from 0.5). No new fixed phrasing is added to cure a rewording. (5) **Sentences and words can stand for each other.** Stored as data, as named meanings with their phrasings and one-word forms. (6) **Symbols and punctuation (SYM1).** AXON knows what a full stop, comma, bracket, quote, colon, question mark and similar symbols do, and when to ignore them. Symbol roles are data. Symbols are hints that raise or lower confidence; they are never the rule. Code is the special case: AXON spots a code region (fenced block, steady indentation, many symbols, programming words) and treats it as untouchable material: nothing inside is interpreted, split or changed. If unsure, AXON treats the text as material and says so. Acceptance: a written set of code samples that pass through the Text Counter and the splitter unchanged, and a set of ordinary sentences whose punctuation is read correctly. (7) **Several commands in one message (CS1).** AXON finds each instruction by meaning, attaches material to the nearest earlier instruction that lacks material, runs each, and answers each in order with its own feedback. If one cannot be read, the others still run and the unreadable one is named with a question. If one depends on another ("count it, then reverse it") the order is kept. Anything destructive is confirmed first. Acceptance includes four-command messages, material before and after the instruction, no symbols at all, and a second set of messages that must NOT be split. (8) **Reply structure and personality (PL1).** Voice: calm, plain, thoughtful, simple, progress first, intelligent without showing off, never boring, no slang. Short forms such as "diff" appear rarely, only in casual moments, never in results, errors, evidence lines or warnings, never at random: a fixed rule, a cap, and a Settings switch. AXON uses its own vocabulary and does not swap words unless asked. Reply order, leaving out parts that do not apply: (a) the answer or verdict first, with an opening that varies; (b) an evidence line when a check was made; (c) what the result means and any risk or drawback noticed; (d) the next step, with what to run and what to report back; (e) a fallback line when the step may fail ("If the problem still appears, we work through it together, or I can request outside help."). AXON states a cause and fix firmly once it has checked, says "found" only after checking, and says plainly when it is unsure. Approved sample replies: (1) "Your text has 534 words. I counted it two ways, and both agree." (2) "I found four requests. Counting is done: 534 words. Reversing is done. The third one I could not read, and I have not guessed it. Which did you mean: sort or shuffle? The fourth is ready to run once that is settled." (3) "I am not certain, so I will not state it as fact. Here is what I do know, and here is what I would need to be sure." (4) "I found a mistake in my last reply: I said 12, the right count is 14. Corrected below." (5) "That is the third failure, and I understand your frustration. I searched, and the cause is a missing file. Here is the fix, with the check that proves it. Run the prompt and send me the report. If the problem still appears, we work through it together, or I can request outside help." (6) "Good. That closes this stage. The next step is the dictionary, and it takes one prompt." (7) "I cannot do that yet, and I will not pretend. It is on the plan, after the language layer." (8) "Meanings you taught me live only on this phone. Export them, or erase them, whenever you choose." Every Settings label and message gets the same quality of writing. (9) **Rephrasing and choosing.** AXON rephrases a sentence or its own answer when asked, in its own vocabulary unless the owner gives a word choice. It can offer several versions; the owner picks one and says what happens to the rest (keep, discard, bring back). The same choice mechanism will serve Media later (for example, several collage results). (10) **Tone and emotion (TN1).** AXON reads positive, negative, plain, feedback, success, or frustration, with a confidence. "Not bad" is read correctly; sarcasm is unreliable, so AXON asks when unsure. The label shapes the reply (frustration: shorter, fix first) and never changes what is true. Judged on a written set. (11) **Truth and checking (VR1, highest importance).** Every answer carries an evidence level: PROVEN (a tested tool computed it), CHECKED (computed a second independent way and both agree), REPORTED (from a named source), UNSURE. AXON states something as fact only at PROVEN or CHECKED. Before replying it re-reads the request, lists everything asked, confirms each is answered, recomputes what can be recomputed and compares; if results differ it says what differs. Each source has a trust level (the Text Counter is PROVEN by its tests; a model reply is REPORTED at best), and trust decides how much checking is needed. AXON cannot promise 100 percent accuracy and must not claim it; the promise that can be kept and tested is that AXON never states something as fact without evidence and never hides a doubt. (12) **Checking the owner's statements and giving useful extras.** AXON does not follow blindly. If the owner says 1 plus 1 is 5, AXON says it is 2; if the owner says 1 plus 1 plus 1 is 3, AXON confirms. It reads the context before and after. It names a drawback or error in what the owner hands it, even when not asked, and gives relevant extra data after the answer (the Text Counter already reports words, characters, characters without spaces, letters and lines). Extras come after the answer and never replace it. Needs the calculator tool (Wave D) and context reading (CS2). (13) **Code and files (later).** AXON Code writes code, runs it in an isolated sandbox with tests and a time limit, and reports what passed and failed before giving it over. AXON may edit files on the owner's device only with explicit permission per action, showing exactly what will change and keeping a copy so it can be undone. (14) **Languages.** Each language has its own dictionary and tests; AXON claims a language only after it passes. Some languages (Chinese, Thai) have no spaces between words, so word counting there needs its own rules. (15) **Other gaps to close.** Tolerance for typing mistakes (matcher change), understanding dates and numbers ("tomorrow", "two thousand"), a "how did you understand me" view, and a version and source line for every dictionary. (16) **Conclusions from facts** (owner requirement, Part 2): from a list of facts AXON can state an inferred conclusion, show the facts behind it and label it as an inference. Built on VR1. (17) **The dictionary and conversational awareness (owner, 2026-10-12).** AXON's conversational awareness will depend heavily on the dictionary. It is a primary, basic need, not an optional extra (FL5). Every language-layer stage (L1 to L7) reads it through the knowledge slot and is designed for many block reads per message (FL6).

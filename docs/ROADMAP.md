## 2. WHAT AXON IS FOR, AND HOW IT MUST FEEL
AXON is an Android app (Capacitor, React, TypeScript; built in Google AI Studio, kept in GitHub, built to an APK by GitHub Actions). It must be an intelligent, truthful, conversational assistant with an English dictionary as its understanding, plus tools and media. It reads what is said and what came before, finds several instructions in one message, answers each, notices mistakes, says plainly what it does not know, and never claims an ability it lacks. Big assistants do this inside one trained model; AXON uses explicit, testable parts and may add a model later as a second tier supervised by those checks. The real work is the language layer; the dictionary is only its first ingredient.
**Design philosophy (owner, 2026-10-16, binding on every screen):** simple, clear, organised, professional. The person must understand a page at a glance: what it does, what they can do, where to go next. No floods of details, long lists or complicated navigation. Show the few main choices first; reveal the rest only when the person goes in (progressive disclosure). A pretty screen that is hard to read is a failed screen. History: an earlier AXON was scrapped because it piled things on top of things until looking at it was painful; the owner saw the same signs again in this one in October. Every screen prompt must say this, and each screen is checked against it. **One look everywhere (decided 2026-10-17):** the same header band on every screen (logo fixed at the left, "AXON" bold with the page name lighter beside it, small-caps line under); the back control is a slim row UNDER the band, never in front of the logo; lists are plain rows (36 px icon, name, chevron), no boxed cards; no per-row "Coming soon" badges (unbuilt items dimmed, one quiet line says so); the Tools home shows group names only. A header may fold away ONLY on editor screens (opt-in, shared ScreenHeader, prompt Q4). Source, Build and Interface Capture screens are locked: do not restyle them.
**Look:** keep the current identity (dark, calm, #ECECEC text, lucide icons, small-caps taglines, header band). Do not add colours, fonts or icon sets. Inspiration from other apps is welcome; the result must look like AXON.

## 7. THE BRAIN (Phase B; designed 2026-10-15)
**Ten stages, each typed, pure, traced (every stage writes a trace entry so "how did you understand me" is real data):** 1 Intake (utterance: text, place, time, id) [B1 done]; 2 Reading (language vs MATERIAL: code, quotes, pasted text never interpreted; symbols) [B1 wraps existing symbols code]; 3 Analysis (tokens with positions, real lemmas, parts of speech and word concepts via the knowledge slot; multi-word entries; per-message block-read budget and cache) [B2: prompt P1 out]; 4 Meaning (the Frame: speech act ask, command, teach, correct, greet, thanks, chat, unknown; predicate concept; typed slots; confidence and alternatives) [B3]; 5 Resolution (match the frame to action schemas declared in the registry by concept distance: synonym 1.0 then hypernym and hyponym decaying; act match; slot completeness; RUN_AT 0.8, ASK_AT 0.5 in src/brain/matcher.ts; below ASK_AT AXON says it does not understand) [B4]; 6 Dialogue (pending questions and choices in src/brain/asking.ts, follow-ups, "more", "it" and "that", topic) [B5]; 7 Planning (several instructions, order, risk and irreversibility questions, permissions, ask for what is missing) [B6]; 8 Execution (handlers run through the kernel with typed arguments, never free text) [B1 legacy handlers, each moves as B4 and B5 retire them]; 9 Verification (check result against request; evidence labels PROVEN, CHECKED, REPORTED, UNSURE) [B6]; 10 Response (compose from the structured result in AXON's voice; fallback block retired at B6) [B1 did CF1].
**Understanding without phrase lists:** words become lemmas (src/brain/dictionary/morphology.ts), lemmas become concepts (the dictionary's synsets: 120,254 sense relations, 234,810 synset relations), a message becomes a Frame from generic English structure (an imperative starts with a verb, a question inverts or uses a wh-word, a teaching message says what something means), the Frame is matched to what each capability says it MEANS ("count", "tally", "enumerate" are one concept). A handler receives arguments, never the text. Ambiguity asks with choices.
**Migration (strangler):** B1 wrapped today's providers as LEGACY HANDLERS (`src/brain/mind/legacy.ts` lists each with the stage that retires it: local rules and dictionary provider B4; taught meanings B5; foundation fallback B6; a test fails if a provider is missing from the register). The GOLDEN TRANSCRIPT (`tests/fixtures/brainGolden.json`, 79 messages) is compared after every Phase B stage: only changes a stage names may differ. A static test forbids regular-expression literals inside `src/brain/mind`. Known weaknesses to fix in order: execution receives only raw text (typed arguments arrive with B4); context fields are optional so order is not type-enforced; a failed stage is traced the same as a not-built one (add "failed"); the trace is discarded by `ask()` (only `askWithTrace()` keeps it); pending-question state lives outside mind (B5 unifies it).
**Honest limits:** early stages understand little; until B4 retires a handler it answers as today; the dictionary has gaps (no place names or people, thin slang), concept matching inherits them (user dictionary UD1 fills them); more stages cost time per message; no promise of 100 percent, the promise is honesty about what is understood. **Self-knowledge (owner, 2026-10-16):** the brain asks the live registry what is online, working or unbuilt; it does not carry fixed lists of its own abilities (done properly in B4, tested by `tests/capabilityTruth.test.ts`).

## 11. LANGUAGE AND VOICE DESIGN
English dictionary one per language, opened on demand; word links exact, near, depends-on-context, related, opposite (only exact and near may replace a word; each replacement lowers the score; a weak guess never runs anything: run at 0.8, ask "Did you mean" from 0.5). Symbols are hints that raise or lower confidence, never rules; code is untouchable material (fenced block, steady indentation, many symbols): nothing inside is interpreted, split or changed; if unsure, treat as material and say so. Several commands per message: find each instruction by meaning, attach material to the nearest earlier instruction lacking material, run each, answer each in order; one unreadable instruction is named with a question while the others run; dependent instructions keep order; destructive ones are confirmed first; a second test set must NOT be split. **Personality:** calm, plain, thoughtful, progress first, no slang; reply order (a) answer or verdict first, (b) evidence line if a check was made, (c) meaning and any risk, (d) next step, (e) fallback line; says "found" only after checking, firm once checked, plainly unsure otherwise.

## 12. LESSONS (real failures)
Tests that do not block the build let defects pass (check by running). Acceptance numbers must be derived, never remembered. A fix proposed from a hypothesis (Tailwind scan) did not cure the failure: measure first. Overloaded builders fail: split. We moved heavy data before measuring the carrier and before the receiving slot existed. A zip is not "the project" until you know what the tool that made it leaves out (the app's Export omitted files; AI Studio's push truncates). A third attempt after two failures breaks FL4 even if tests pass. A small answer can be a display limit, not a data limit (8 meanings in data, 3 shown). A reply that starts work without the Law Check breaches FL11. Adding phrases is not building intelligence (FL13). A prompt tied to a base names a file only that base has. A golden transcript recorded from new code proves nothing alone: replay it against the old code (done for B1). Reading a 300,000-character roadmap cost whole accounts: keep this file small.
